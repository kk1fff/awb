# Project context and specialist sessions

Start with `get_project_info`, `get_designer_status`, and `get_workspace_context`. If the human supplied a goal and project goal is empty, write it with `update_project_info` using the current `info_revision`. The main session's goal follows the project goal: passing `goal` to `update_workspace_context` there returns `PROJECT_GOAL_ONLY`, even after the project goal is set. Use `update_workspace_context` for a specialist goal or for acceptance criteria, constraints, current task, work status, and summary. Context edits do not increment `sceneRevision`.

The human-launched agent in the main session is the lead. For substantial independent scene parts, the lead calls `reserve_designer_slot` before creating a host-runtime subagent and gives it the reservation ID and task. The concurrent limit includes the lead and defaults to four. Handle smaller tasks directly when delegation adds no value. Fieldwork only tracks slots and scene sessions; the host agent runtime creates and communicates with subagents.

The specialist calls `open_designer_session` with its reservation, works in its own workspace, and passes its returned `sessionId` on every scene tool call. It renders, opens and inspects the PNG, saves, and calls `complete_designer_session` with a handoff summary. The lead reviews the actual result and handoff, incorporates accepted work explicitly, then calls `confirm_designer_session` to free the slot. Call `abort_designer_slot` if a reservation cannot be used.

Manual specialist shells use `fieldwork session create --name "..." --goal "..."` and `fieldwork session shell <uuid>`. The browser can inspect a session at `/?workspace=<uuid>`. Keep designer scene work paused while shared application source is being changed; resume from a fresh scene after the fix is reviewed. Workspace archive and restore are reversible; purge is permanent and requires the exact UUID. The `tools` guide covers the corresponding HTTP endpoints.

For HTTP clients, `GET`/`PATCH /api/project` handles project metadata, and `GET /api/designers` plus the reservation/session routes handle designer capacity and lifecycle. `GET`/`POST /api/workspaces` lists or creates sessions; `GET /api/workspaces/<uuid>` and `GET`/`PATCH /api/workspaces/<uuid>/context` read or update one session. Archive, restore, and purge use the corresponding `/api/workspaces/<uuid>` action routes. A specialist's ordinary scene routes are scoped under `/api/workspaces/<uuid>/`.

Project and designer HTTP routes: `GET /api/project`, `PATCH /api/project`, `GET /api/designers`, `POST /api/designers/reservations`, `POST /api/designers/reservations/:reservationId/open`, `POST /api/designers/sessions/:sessionId/complete`, `POST /api/designers/sessions/:sessionId/confirm`, and `POST /api/designers/reservations/:reservationId/abort`.

Workspace HTTP routes: `GET /api/workspaces`, `POST /api/workspaces`, `GET /api/workspaces/:workspaceId`, `GET /api/workspaces/:workspaceId/context`, `PATCH /api/workspaces/:workspaceId/context`, `POST /api/workspaces/:workspaceId/archive`, `POST /api/workspaces/:workspaceId/restore`, and `DELETE /api/workspaces/:workspaceId`.
